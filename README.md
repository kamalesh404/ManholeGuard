# MANHOLEGUARD

**Smart IoT-Based Manhole Safety Monitoring System** — a real-time industrial
safety monitoring dashboard for municipal manhole networks.

The interface is built around one question: **is this manhole safe right now?**

> **DEMO DATA** — this prototype runs entirely on simulated telemetry. No values
> come from a physical ESP32. The badge in the header and the control bar at the
> bottom of the screen mark this clearly.

## Run it

```bash
npm install
npm run dev        # http://127.0.0.1:5183
npm run build      # typecheck + production build
npm run typecheck
```

## Pages

| Route | Purpose |
| --- | --- |
| `#/` | **Live Monitor** — primary screen: large safety state, gas monitors, water level, current risk, device health, cover/tamper, fleet, alerts, system overview, cutaway visual, schematic map |
| `#/manholes` | Fleet of monitored manholes with latest telemetry |
| `#/manholes/MG-001` | Manhole detail — full telemetry table with recent trends |
| `#/alerts` | Alert log with severity/manhole filters and acknowledge actions |
| `#/devices` | ESP32-C3 controllers and their health |
| `#/settings` | Gas units (ppm vs raw ADC), poll interval, alarm thresholds |

## Simulation controls

The **DEMO DATA** bar forces the selected manhole into any state:

`SAFE` · `WARNING` · `HIGH RISK` · `CRITICAL` · `OFFLINE`

Changing the state updates, in one step: the ambient background tint, the large
status banner, the relevant sensor cards, the Current Risk explanation, the
alert log and the fleet summary.

## Data architecture

The UI is written against plain data types in `src/model/types.ts` —
`Manhole`, `Device`, `Telemetry`, `SensorEval`, `Alert` — and never against
example values.

All data enters the app through one seam, `TelemetryProvider`
(`src/data/simulator.ts`):

```ts
export interface TelemetryProvider {
  readonly kind: 'simulated' | 'live';
  readonly label: string;
  poll(ctx: PollContext): Record<string, Telemetry>; // keyed by manholeId
}
```

`Telemetry` carries exactly what an ESP32-C3 firmware would publish:

```
manholeId, timestamp, gasUnit, ch4, co, h2s, waterLevel, temperature,
humidity, coverStatus, vibration, battery, wifiStatus, signalStrength,
deviceStatus
```

To go live, implement `TelemetryProvider` against your gateway
(`GET /api/telemetry`, MQTT bridge, WebSocket…) returning the same shape and
swap the singleton in `src/state/store.tsx`. No component changes are required.

### Units and honesty

`gasUnit` is part of the payload:

- `ppm` → values are displayed as calibrated ppm.
- `raw` → values are displayed as **raw ADC counts** with a `RAW SENSOR LEVEL`
  tag. Raw counts are never presented as ppm. Thresholds are configured per
  unit mode (`src/model/evaluate.ts`, editable in Settings).

### Status evaluation

`assess()` in `src/model/evaluate.ts` classifies every channel against the
configured thresholds and derives:

- overall status: `safe | warning | high | critical | offline`
- per-sensor states for the cards
- the human-readable **Current Risk** lines (the *why* behind the state)

Alerts are generated by diffing consecutive frames: whenever a sensor escalates
or the device drops its heartbeat, an alert is raised with the concrete reason
(e.g. `H₂S 32 ppm above critical threshold (25)`).
